[[programming_model]]
== Programming Model
:imagesdir: ../images

=== Instruction stream

AME instructions are in-line with other instructions on the hart.
They are executed in program order, and their memory accesses follow RVWMO at the
instruction level (see <<ame-consistency-model>>).

[[ame-state-enablement]]
[[ame-common-state-access]]
==== AME state enablement

AME adds a two-bit matrix context status field, `MS[1:0]`, to `mstatus`.
It is shadowed in `sstatus` and follows the `VS[1:0]` state model.

.Encoding of the `MS[1:0]` status field
[cols="1,1,3",options="header"]
|===
|Encoding |Status |Meaning

|`0`
|Off
|AME state is disabled.

|`1`
|Initial
|AME state is enabled and initial.

|`2`
|Clean
|AME state is enabled and matches its saved image.

|`3`
|Dirty
|AME state is enabled and might differ from its saved image.
|===

Initial, Clean, and Dirty enable AME state. An AME operation that might modify
that state changes each applicable Initial or Clean field to Dirty unless the
operation specifies another result. An implementation may set Dirty
conservatively. Dirty sets the corresponding `SD` bit.

Privileged software may set `MS` to Clean after saving AME state. Writing `MS`
does not modify AME state. `MS` resets to Off; a hart without AME may make it
read-only zero.

When the hypervisor extension is present, `vsstatus` contains an `MS[1:0]`
field. When `V=1`, both `mstatus.MS` and `vsstatus.MS` are applicable. AME is
enabled only when every applicable field is non-Off, and state changes update
every applicable field. A Dirty `vsstatus.MS` sets `vsstatus.SD`.

[[shared-ame-backend]]
==== Shared AME backend

An AME backend contains the execution resources and architectural context
state. It may be shared by multiple harts. Base AME exposes the entire backend
as one indivisible ownership unit, held by at most one software execution
context.

[[ame-backend-ownership]]
===== Ownership and access rules

The read-only `ameown.OWNED` field reports whether the current context owns the
backend. `ame.acquire` requests ownership and `ame.release` relinquishes it;
<<ame-backend-management-operators>> defines their semantics.

If any applicable `MS` field is Off:

* Every AME instruction raises an illegal-instruction exception, including
  `ame.acquire` and `ame.release`.
* Every read or write of every AME CSR raises an illegal-instruction exception,
  including a read of `ameown`.

If every applicable `MS` field is non-Off but `ameown.OWNED=0`:

* Every AME instruction other than `ame.acquire` and `ame.release` raises an
  illegal-instruction exception.
* Every access to a writable AME context CSR raises an illegal-instruction
  exception.
* Read-only capability CSRs and `ameown` may be read.

These exceptions precede all other AME validation and change no AME state.

If `ameown.OWNED=1`, a CSR instruction that attempts to set any applicable
`MS` field to Off raises an illegal-instruction exception and changes no state.
No implicit release occurs; software must execute `ame.release` first.

[[ame-backend-ms]]
===== Interaction with `MS`

A newly granted backend is bound to the current context in architectural
initial state, with `ameown.OWNED=1` and each applicable `MS` field Initial.
Reacquiring an already-owned backend preserves its state and `MS`. Releasing
an owned backend clears `OWNED` and sets each applicable `MS` field to Initial.
`MS` alone does not grant ownership.

[[ame-backend-context-switch]]
===== OS context switch

Software saves `ameown.OWNED` with the execution context. Before switching out
an owner, it saves required AME state and releases the backend.

To restore a saved owner, software enables `MS`, executes `ame.acquire`, and
waits for success. It then restores any saved AME state and sets `MS` to Clean,
or retains the initial state and Initial status established by acquisition.
AME execution resumes only after acquisition succeeds and any required restore
completes.

=== State

An acquired AME backend binds its AME registers and writable context CSRs to
the current software execution context. AME instructions access that state and
control data transfer between AME registers and memory.

.Register state and data movement paths for AME. The F/D and V extensions are _optional_ with AME. The only architectural datapath between vector (if present) and AME is through memory. The scalar datapath(s) is/are one-way. AME accumulator state can only be moved to/from the AME matrix registers.
image::ame_state.svg[AME state and architectural datapaths]

The `Acc` registers are used to accumulate the output of partial matrix multiplies.
The `M` registers are general-purpose matrix registers.
They are used for anything that is not an accumulation, including the data operand of load or store instructions,
the input operands of 1D (element-wise/vector) operations, and the output operands of 1D operations.

A single `M` register may hold multiple, one, or part of a square,
depending on implementation-defined parameters and programmed datatype.
Generally, the number of squares that will fit in an `M` register is inversely proportional
to the datatype size (because larger datatypes require more storage).

In contrast, an `Acc` register always holds exactly one square.

=== Squares

The *pack_factor* of a datatype is the number of squares contained in a single M register:

* **Packed** (`sizeof(dtype) < AME_UNIT_DATATYPE_SIZE`): `pack_factor = AME_UNIT_DATATYPE_SIZE / sizeof(dtype)`
* **Unit or Wide** (`sizeof(dtype) >= AME_UNIT_DATATYPE_SIZE`): `pack_factor = 1`

Every supported datatype size is a power of two.  Equivalently, since
`AME_UNIT_DATATYPE_SIZE` is itself a power of two: a packed datatype size must
divide the unit size, and a wide datatype size must be a power-of-two multiple
of it.  A datatype that does not satisfy this rule is reported as unsupported
through `amestatus.UN`.  Consequently the `ceil` in the general group-size
formula is equal to exact division for every supported wide datatype, and every
M-register group spans a power-of-two number of registers.

When the programmed datatype is a *packed datatype*
(size < `<<ame:doc:param:AME_UNIT_DATATYPE_SIZE,AME_UNIT_DATATYPE_SIZE>>`),
a single M register holds `pack_factor` logical squares.

The number of elements processed by an AME matrix multiply instruction depends on the datatype.
For non-packed datatypes (`pack_factor = 1`), the operands are `N x N` squares.
When operand formation produces `N_sq > 1`, the input operands span
`N x (N_sq * N)` and `(N_sq * N) x N` elements respectively, while the
accumulator output remains `N x N`.

[NOTE]
--
This constraint keeps the ISA simple: instruction encoding does not need per-operand shape fields
and register mapping is uniform. The accumulator operand always holds exactly one `N x N` square.

For contrast, general matrix multiply on non-square inputs (`M x K` by `K x N`) produces `M x N`.
AME handles this by tiling into squares and zero-padding boundary tiles in software.

.Example (`N = 8`)
* Multiply `A(3x5)` by `B(5x2)`.
* Software packs `A` and `B` into zero-padded `8x8` squares.
* AME computes a full `8x8` result square.
* Software keeps only the valid `3x2` upper-left region and discards padded rows/columns.
+
image::ame-square-padding-example.svg[Matrix padding example for N=8]

Larger non-square problems are handled the same way: process full interior `N x N` tiles normally,
and pad only edge tiles.
--

The row/column dimension, N, is implementation-defined and is equal to the
square root of <<ame:doc:param:AME_NELEM,AME_NELEM>>.
<<ame:doc:param:AME_NELEM,AME_NELEM>> can be any power of 4.

[NOTE]
--
It is possible to create portable AME binaries regardless of the chosen value of
<<ame:doc:param:AME_NELEM,AME_NELEM>>.

Highly-tuned binaries may produce a better result by targeting a specific value of
<<ame:doc:param:AME_NELEM,AME_NELEM>>, similar to how auto-vectorizing compilers can generate
more efficient code for RISC-V Vector when VLEN is known.
--

All elements within a single square have the same datatype, for example unsigned 8-bit integer or
single-precision IEEE floating point.

A single operation may reference squares with different datatypes (for example, 8-bit integer inputs widening to a 16-bit integer output).
Mixed-datatype operations are optional; see <<datatypes>> for the implementation discovery mechanism.

[[mapping-squares-to-m-registers]]
==== Mapping squares to M registers

A single square (vector or matrix) may fit in one `M` register or may span multiple consecutive
`M` registers, depending on the datatype size.
If the datatype is no wider than <<ame:doc:param:AME_UNIT_DATATYPE_SIZE,AME_UNIT_DATATYPE_SIZE>>,
one register is sufficient;
wider datatypes require additional registers.
The required register count is the datatype size rounded up in units of
<<ame:doc:param:AME_UNIT_DATATYPE_SIZE,AME_UNIT_DATATYPE_SIZE>>
(that is, `ceil(sizeof(datatype)/AME_UNIT_DATATYPE_SIZE)`).

When a square requires multiple consecutive `M` registers, consecutive registers are combined into a group.
When registers are grouped, the register index must be a multiple of the group size (_e.g._, when
group size is two, register indices must be even).
Specifying a register index that is not a multiple of the group size results in an
Illegal Instruction exception.
This mechanism is analogous to the `LMUL` facility used in the RISC-V vector (`V`) extension.

Packed datatypes can be used directly as operands in compute instructions;
see <<operand-formation>> for how multi-operand instructions determine register spans.

.Square-to-M-register mapping examples
image::ame-square-reg-mapping.svg[Square to M register mapping examples]

When an `M` register is part of a group, only the lowest-indexed register of that group may be used directly in operations.
Using any other register in the group raises an `Illegal Instruction` exception.

// not really bash, but it gets us colored # comments
[source,bash]
----
# precondition:
# a square is in m[2-3]

madd.ew m2, m2, m2  # well-defined, m2 = m2 + m2

madd.ew m2, m3, m3  # raises Illegal Instruction
madd.ew m3, m2, m2  # raises Illegal Instruction
----

[[operand-formation]]
[[ame-common-register-groups]]
==== Operand formation

When a compute instruction references multiple tensor operands, all operands must contain
the same total number of squares.
The instruction's square count is `N_sq = max(pack_factor)` across all tensor operands.

Each operand's register span is then sized to hold exactly `N_sq` squares:

* **Packed operand** (`pack_factor > 1`): `N_sq / pack_factor` registers
* **Unit or Wide operand** (`pack_factor = 1`): `N_sq x ceil(sizeof(dtype) / AME_UNIT_DATATYPE_SIZE)` registers


Consider an ADD instruction with three tensor operands of different datatypes:

.Operand formation example (`AME_UNIT_DATATYPE_SIZE` = 8 bits)
[cols="1,1,1,1,1",options="header"]
|===
| Operand | Dtype | pack_factor | Register Span | Total Squares

| Tsrc0 | Int4  | 2 | N_sq / 2 = 1 register  | 2
| Tsrc1 | Int8  | 1 | N_sq x 1 = 2 registers | 2
| Tdst  | Int16 | 1 | N_sq x 2 = 4 registers | 2
|===

`N_sq = max(2, 1, 1) = 2` (set by the Int4 operand with `pack_factor = 2`).
All three operands contain `N_sq x AME_NELEM = 2 x AME_NELEM` elements total.

Accumulator (`Acc`) operands are not subject to this rule:
they always hold exactly one square regardless of datatype.

This rule applies uniformly to both 1D (element-wise) and 2D (matrix multiply) instructions.
For 1D instructions, each operand processes `N_sq` squares element-wise — a packed
operand's `pack_factor` squares are stored contiguously in a single register, while a
non-packed operand's `N_sq` squares span `N_sq` registers.
For 2D matrix multiply instructions, the inner product dimension extends to
`N_sq * N` elements; see <<_2_dimensional_matrix_multiply_operations>>.

`mpack.ew.x` and `munpack.ew.x` are explicit exceptions to this general
multi-operand rule.  They transfer one selected logical square and preserve or
ignore the other packed slots as specified.  Their instruction-specific
operand-formation rules take precedence over `N_sq = max(pack_factor)`.
`mconv.ew`, by contrast, follows the general rule: its source and destination
datatypes may each be packed or non-packed, and both operands span `N_sq`
squares like any other elementwise instruction.

`mcolunzip.ew`, `mcolzip.ew`, `mrowunzip.ew`, and `mrowzip.ew` are also
explicit fixed-shape exceptions.
They perform one two-square transformation rather than repeating a one-square
transformation `N_sq` times.  Each operand is both a source and a
destination: each instruction consumes the sole square from each of `ms1`
and `ms2` and writes the two result squares back into `ms1` and `ms2`, so
no separate destination operand is allocated and each operand spans only its
own register requirement.  `ms1` and `ms2` must name distinct M registers;
an equal pair raises an `Illegal Instruction` exception before any register
is read or written.

All Permutation instructions -- the row/column broadcast, gather, scatter,
and shift forms together with the fixed-shape zip/unzip forms -- support only
datatypes whose size is no smaller than `AME_UNIT_DATATYPE_SIZE`; a packed
datatype follows <<norm:ame_op_supported_contract>>.  The broadcast, gather,
scatter, and shift operands therefore always form exactly one logical square
(`N_sq = 1`).

For `mcolgather.ew`, `mrowgather.ew`, and all four scatter instructions, the
low 32 raw bits of each matrix-index element form an unsigned value; any higher
element bits are ignored, and an element narrower than 32 bits is zero-extended
to U32.  The index is the low `log2(sqrt(AME_NELEM))` bits of that U32 value;
higher U32 bits are ignored, so an index element never raises an exception
regardless of its value.

[#norm:ame_nsq_1d]#For an ordinary 1D element-wise instruction, the logical
element count is `N_sq * AME_NELEM`.  The operator is applied to corresponding
logical elements of every operand over that entire range.# Instruction
operation formulas that use a single element index apply over this complete
range, including every packed or wide logical square.

[#norm:ame_nsq_structural]#Prefix and reduction instructions apply their
documented `N x N` transformation independently to each of the `N_sq` logical
squares.# A row or column index is local to its square and cannot address
another logical square.  A formula showing one `N x N` transformation
therefore applies independently for `sq = 0 .. N_sq-1`, with logical element
indices offset by `sq * AME_NELEM`.

[#norm:ame_nsq_matmul]#For a 2D matrix multiply, let `A_s` and `B_s` denote
logical square `s` of the two formed operands, for `s = 0 .. N_sq-1`.  Every
result sums `N_sq * N` products across corresponding square pairs, and each
accumulator result remains one `N x N` square.# For an untransposed multiply,
placing all `A_s` side by side and stacking all `B_s` expresses this as an
`N x K` by `K x N` product with `K = N_sq * N`.  A transposed variant
transposes each `N x N` logical square before summing its product; it does not
transpose either aggregate rectangular matrix.

==== Operand validation and exception priority

Every encoded `M` or `Md` register specifier is validated immediately after
decode and before any `Md` or `M` state is read.  Thus an index greater than or
equal to `AME_NUM_M_REGS` raises an Illegal Instruction exception before any
datatype-dependent validation.
For the `mcolunzip.ew`, `mcolzip.ew`, `mrowunzip.ew`, and `mrowzip.ew`
instructions, the requirement that `ms1` and `ms2` name distinct M registers
is likewise checked immediately after decode, together with these base-index
checks; an equal pair raises an Illegal Instruction exception.
Datatype compatibility between the two operands is a separate operand-class
requirement: a datatype mismatch reports `amestatus.UN` rather than an
exception.

Every encoded `Acc` or `Ad` register specifier is likewise checked immediately
after decode and before any `Ad`, `Acc`, or datatype-dependent `M` state is
read.  An index greater than or equal to `AME_NUM_ACC_REGS` is handled according
to <<ame:doc:param:AME_UNIMPL_ACC_BEHAVIOR,AME_UNIMPL_ACC_BEHAVIOR>>.  All
encoded M/Md and Acc/Ad base-index checks therefore precede datatype-support
checks and any `amestatus.UN` report.  A derived accumulator span, such as the
packed span used by `mmov.m.a` or `mmov.a.m`, is checked after the operation
tuple is supported but before any operand data access or architectural write.

After the required datatypes and operation tuple have been found to be
supported, but before any `M` data access or architectural write, each tensor
operand is formed according to <<operand-formation>>.  Its base, per-square
alignment, and complete physical-register span are then validated.  The
complete span, rather than only the first square's group size, is checked.  A
zero-sized span, a misaligned group, or a group whose final register would be
outside the implemented register file raises an Illegal Instruction exception.

For an instruction that does not use the multi-operand `N_sq` rule, the same
validation applies using the physical span explicitly defined by that
instruction.  Existing per-instruction base and alignment tests are redundant
clarifications of these common checks and do not alter this exception
priority.  An unsupported datatype or operation sets `amestatus.UN` only after
all encoded base indices have passed the first-stage index check; group
alignment and span are not interpreted for an unsupported datatype.

Every logical source element is read from the complete formed operand in
logical row-major order.  A wide square is assembled from its complete
register group before the implementation-defined register layout is converted
to logical row-major order.  Packed slots and `N_sq` squares participate in
the logical element sequence defined in <<operand-formation>>; implementations
must not derive element locations using a truncated per-register element
count.

[[register-group-overlap]]
==== Register group overlap and atomic writeback

Register operands name groups rather than individual storage locations, so two
operands can overlap completely or partially when their datatypes require
different register spans.

[#norm:ame_register_group_overlap]#Unless an instruction explicitly states an
overlap restriction, any source `M` or `Acc` register group may overlap any
destination register group, including complete overlap where the base register
numbers are equal.#

[#norm:ame_source_snapshot]#All source register values, source datatype values,
scalar operands, and index operands are read from the architectural state that
exists immediately before the instruction begins.# Consequently, an
instruction such as a gather, broadcast, shift, or reduction produces the same
result when its destination overlaps a source as it does when the destination
is disjoint.  Writes performed by the instruction do not change the source
snapshot used by later element operations.

[#norm:ame_atomic_register_writeback]#For register-only AME instructions, all
destination `M`, `Md`, `Acc`, and `Ad` writes are staged and become visible
together only after every operand, datatype, alignment, bounds, and index check
has completed successfully.# Accrued status-flag updates to `amefflags` and
`amexsat` are staged in the same way and commit together with the destination
writes.

[#norm:ame_register_exception_atomicity]#If a register-only AME instruction
raises a synchronous exception, none of its staged destination writes commit;
only architectural trap state written by exception handling may change.# Such
an instruction likewise commits no staged `amefflags` or `amexsat`
update.  An
unsupported datatype or operation is not a synchronous exception: it sets
`amestatus.UN` and returns without committing any destination write, as
described in <<datatypes>>.

=== Polymorphic instructions

AME instructions do not encode operand datatypes; instead, datatypes are determined by dedicated datatype registers.

[NOTE]
This feature makes AME analogous to polymorphic programming languages
– a single function (instruction) is defined for all datatype combinations (polymorphic argument types).

[[ame-common-datatype-support]]
=== Datatypes

AME supports up to `2^32 - 1` unique datatypes, half of which are reserved for custom use.
The value 0 is reserved to mean uninitialized.

[NOTE]
--
The datatype registers are similar to WARL CSR fields, so implementations only need to support
enough state to represent the datatypes they support.

For example, an implementation that only supports two datatypes would only need two bits to
represent those datatypes plus uninitialized.
--

Standard datatypes and encoding rules are listed in <<datatypes>>.

Implementations may choose which standard datatypes are supported and which custom datatypes
are supported.

[#norm:ame_op_supported_contract]#An instruction datatype tuple is unsupported
when a required datatype is zero or unknown, the operation is not implemented,
the datatype classes do not meet the instruction requirements, or the
implementation does not support that exact operation/datatype combination.#
An unsupported tuple sets `amestatus.UN` and leaves every destination register
unchanged; it does not raise a synchronous exception.

[#norm:ame_op_supported_defined_result]#Once an implementation accepts an
operation/datatype tuple, the result is the mathematical operation stated by
the instruction, interpreted and converted according to the common datatype
rules in this chapter.#

[#norm:ame_op_precondition]#No source data is consumed and no destination data
is produced until the encoded indices and required datatype tuple have passed
their common validation checks.#

[#norm:ame_op_result_width]#An element result is represented in the destination
datatype.  Bits outside that datatype representation are not architectural
state and cannot affect a later AME operation.#

Data-scalar `.ew.x` instructions interpret exactly the low
`sizeof(amestype)` bits of the X-register operand when XLEN is at
least that width, ignoring any higher X-register bits.  When the scalar
datatype is wider than XLEN, the X-register bit pattern is zero-extended to
that width.  The resulting bit pattern is interpreted using
`amestype`, converted to the tensor source datatype, and then used by
the ordinary same-datatype element operation.  A
failed scalar conversion is an unsupported datatype tuple.  Control scalars,
including indices, offsets, shift amounts, strides, and packed-slot selectors,
are unsigned or signed integer quantities defined by their instruction; they
do not use `amestype`.

A legal implementation may support either zero standard datatypes or zero custom datatypes (i.e.,
all custom or all standard).

[NOTE]
--
Profiles will likely mandate a minimal set of supported datatypes.
--

`M` register datatypes are set using the <<ame:doc:inst:msettyp,msettyp>> instruction and
read using the <<ame:doc:inst:mgettyp,mgettyp>> instruction. `Acc` register datatypes are
set using <<ame:doc:inst:asettyp,asettyp>> and read using
<<ame:doc:inst:agettyp,agettyp>>. Setting an `Acc` datatype with `asettyp` also clears the
corresponding accumulator tile.

The clear performed by `asettyp` and `msettyp` writes all-zero physical storage
bits; it does not produce the datatype's semantic zero.  `msettyp` derives the
group size from the newly requested datatype, validates the base alignment and
complete span, and clears every physical M register in that group.  Unsupported
datatype requests set `amestatus.UN` and leave both descriptor and data state
unchanged.

=== Data movement

Data movement between AME register files, the integer (X) register file, the floating point (F)
register file, and memory are restricted in order to facilitate a detached AME execution unit.

There are no AME data movement instructions between memory and the `Acc` registers;
rather, `Acc` registers can only be moved in to or out of the `M` registers.

`M` register data can be loaded and stored from/to memory; <<ame-common-memory>>
specifies those transfers.

A scalar from the X register file can be sent to an `M` register.

AME does not define data movement operations between AME register files and the vector (V)
register file.
Performance-sensitive AME code should use AME 1D operations on matrix data rather than RISC-V Vector.

[[ame-common-memory]]
=== Memory

This section is the common contract for the ten load and store instructions
enumerated in <<Load and store>>.  It defines their memory layouts, their
base-address alignment requirement, their exception behavior, and the ordering of
AME memory transfers with respect to the other memory accesses of the hart.

AME uses the same address space as the host hart.
In systems with virtual memory, AME loads and stores go through (H)S-mode translation and,
if applicable, G-stage translation when run within a hypervisor.
They are subject to the same address translation, protection, physical-memory
attribute, and access-fault checks as ordinary RISC-V memory accesses.  Within
each element, increasing byte addresses correspond to successively more
significant groups of eight bits; the lowest-addressed byte contains bits 7:0.

For every memory instruction, let `E` be the element size in bits, `P = pack_factor`,
and `N = sqrt(AME_NELEM)`, so that `AME_NELEM = N * N`.  For an interoperability or
strided instruction `E = sizeof(dtype)`, the size of the programmed datatype.  For
`mls.1r` and `mss.1r`, `E = AME_UNIT_DATATYPE_SIZE` and `P = 1`: those instructions fix
the element size instead of reading it from a datatype register.  These three abbreviations are local to this section; the
instruction pages spell the same quantities out as `sizeof(Md[md])`,
`pack_factor`, and `sqrt(AME_NELEM)`.  Sizes written as `sizeof(...)`, as `E`,
or as an `AME_*_SIZE` parameter are counts of bits, while every quantity whose
name ends in `_bytes` is a count of bytes.  Elements are packed
back-to-back as E-bit fields; no byte padding is inserted between elements.
The first field occupies the low E bits of the transfer bit string, and the
byte at the lowest address contains bits 7:0 of that string.  When the final
field does not end on a byte boundary, a load ignores the unused high bits of
the final byte and a store writes those unused high bits as zero.

For a row-major or column-major interoperability transfer, the complete bit
string contains `P * AME_NELEM * E` bits and
`total_bytes = ceil(P * AME_NELEM * E / 8)`.  Packed squares occur in ascending
slot order; within each square, elements occur in the instruction's stated
row-major or column-major order.

For a strided transfer, the segment addresses are derived as follows.  `base` is
the unsigned XLEN-bit value `X[rs1]`, and `stride` is the unsigned XLEN-bit
value `X[rs2]`.  Each segment begins at
`(base + seg * stride) modulo 2^XLEN`; the resulting XLEN-bit address is then
subject to the ordinary translation, protection, and access checks described
above.  Each segment is a separately byte-rounded bit string:

* `.st` has `N` segments.  Segment `i` contains `P * N * E` bits and
  `seg_bytes = ceil(P * N * E / 8)`; element `(sq,i,j)` starts at bit offset
  `(sq * N + j) * E` within that segment.
* `.tst` has `P * N` segments.  Segment `sq * N + j` contains `N * E` bits
  and `seg_bytes = ceil(N * E / 8)`; element `(sq,i,j)` starts at bit offset
  `i * E` within that segment.

Strided stores permit segment address ranges to overlap, including when
`stride` is zero.  Their final memory image is the result of staging segments
in ascending segment-number order and bytes within each segment in ascending
byte-offset order; a byte from a later segment therefore wins any overlap
with an earlier segment.  This ordering selects the staged result but does not
permit partial completion: if any access faults, none of the staged bytes are
written.

`mls.1r` and `mss.1r` transfer exactly
`AME_MATRIX_REGISTER_SIZE / 8` bytes.  Their transfer
bit string is the physical M-register raw bit pattern: the lowest-addressed
byte transfers physical bits 7:0, and subsequent byte addresses transfer
successively more-significant groups of eight physical bits.

Every memory instruction requires its base address to be naturally aligned to
`element_bytes = ceil(E / 8)`, the byte size of one element.  A base address that is
not so aligned raises an address-misaligned exception, as specified in
<<Memory exceptions>>.  Because `mls.1r` and `mss.1r` fix `E` at
`AME_UNIT_DATATYPE_SIZE`, their requirement is the same on every transfer and does not
depend on any datatype register.

No other alignment is architecturally required.  In particular the transfer
size, the segment size, and the value of `stride` place no constraint on the
base address, and a transfer may begin and end at any offset within a page.

[NOTE]
--
`element_bytes` is one byte for every datatype of eight bits or fewer, so those
datatypes carry no alignment requirement at all; for every other supported
datatype it is a power of two, because every supported datatype size is a power
of two (see <<Squares>>).

Element alignment is the weakest requirement under which every element of an
interoperability transfer is itself naturally aligned, because elements are
packed at a fixed `E`-bit pitch measured from the base address.  A buffer
written by `mss.rm` or `mss.cm` can therefore be consumed element-wise by
ordinary base-ISA loads without depending on misaligned scalar access support.
A naturally aligned power-of-two element cannot cross a larger power-of-two
boundary, so no element straddles a page boundary, nor a cache block boundary in
an implementation whose cache blocks are at least as large as one element.  A strided
transfer extends the same property to every segment when `stride` is also a
multiple of `element_bytes`; software that intends scalar consumption of a
strided region should choose such a stride.

An implementation may complete more strongly aligned transfers faster, and a
profile or ABI may mandate stronger alignment.  The architecture does not:
software that wants block-aligned or page-aligned buffers can always align them
itself, whereas a stronger architectural requirement could not be relaxed by
software.
--

==== Square memory access

AME provides memory storage variants that operate on one of three memory layouts:

*  Row-major (`mls.rm` / `mss.rm`)
*  Column-major (`mls.cm` / `mss.cm`)
*  Whole register (`mls.1r` / `mss.1r`)

The row-major and column-major variants are called the _interoperability_ storage instructions.
They transfer data as a contiguous block — no striding, partial-tile, or predicated variants
exist.  A non-packed datatype transfers one square between memory and one M register, or a
group of them for a wide datatype, while a packed datatype transfers `pack_factor` squares in
a single instruction.

.square memory access example for packed datatypes
image::packed-square-instructions.png[Packed square load/store illustration]

* **Load:** `pack_factor` squares are loaded from contiguous memory and packed into a
  single M register.

* **Store:** The single packed M register is unpacked and `pack_factor` squares are written
  to contiguous memory using the same layout.

The whole-register instructions (`mls.1r`, `mss.1r`) transfer one physical M register
in row-major order at a fixed element size of `AME_UNIT_DATATYPE_SIZE`, which is exactly
one register's worth of elements because
`AME_MATRIX_REGISTER_SIZE = AME_NELEM * AME_UNIT_DATATYPE_SIZE`.  They behave as
`mls.rm` and `mss.rm` do for a unit datatype, except that the element size is fixed by
the instruction rather than taken from a datatype register.
They therefore neither read nor require a supported datatype, which is what register
spilling, context switching, and calling conventions need: the register is saved and
restored whatever its programmed datatype happens to be, including an uninitialized or
unsupported one.  A wide logical square that occupies multiple M registers requires one
instruction for each register in the group.

==== Strided memory access

AME provides strided storage variants that transfer a square between an `M` register and a
non-contiguous region of memory:

*  Strided (`mls.st` / `mss.st`)
*  Transposed strided (`mls.tst` / `mss.tst`)

The strided variants access memory as a sequence of equally spaced segments, one segment per
row of the square, with consecutive segments separated by a programmable byte stride.
The transposed strided variants apply the same access pattern to the transpose of the square:
rows of the square in the `M` register map to columns of the memory region.
Both support non-packed and packed datatypes; for a packed datatype the `.st` forms place the
sub-squares side by side within each row, while the `.tst` forms stack them vertically.
Segment counts, segment sizes, and within-segment bit offsets are given by the rules above,
which also establish that sub-byte elements are never assigned separate byte addresses.

.strided memory access example for packed datatypes
image::packed-strided-instructions.png[Packed strided load/store illustration]

==== Memory exceptions

An interoperability or strided load or store that names an `M` register whose
programmed datatype is unsupported sets `amestatus.UN` and makes no other
architectural state change — neither the `M` register group nor memory is modified.
This is an unsupported-operation report as described in <<datatypes>> and not a
synchronous exception, but it is defined here because it precedes both exception
classes below in the check order.
`mls.1r` and `mss.1r` do not read `Md` and are therefore not subject to it.

In addition to the illegal-instruction exceptions covered by
<<Operand validation and exception priority>>, AME load and store instructions raise
two classes of precise exception:

* **Address misaligned:** A typed load or store whose base address is not
  naturally aligned to `element_bytes` raises an address-misaligned exception — `Load address
  misaligned` for a load and `Store/AMO address misaligned` for a store.  The exception is
  raised before any memory access is attempted: the instruction commits no update to its
  destination `M` register group and performs no explicit data-memory write.  The
  `mls.1r` and `mss.1r` are subject to it with `E` fixed at `AME_UNIT_DATATYPE_SIZE`.

* **Memory fault:** When a load or store takes any fault the base architecture defines
  for an explicit memory access — a page fault, guest-page fault, access fault,
  protection failure, or PMA violation among them — the precise exception is reported
  through the standard RISC-V trap mechanism.  If the applicable `xTVAL` CSR is written with a nonzero
  value, it contains the virtual address of the portion of the access that caused the fault.
  For a strided transfer that address lies within the faulting segment and need not lie in
  the same page as the base address.
  No partial completion is permitted: the faulting instruction commits no update to its
  destination `M` register group and performs no explicit data-memory write, neither to the
  faulting portion of the access nor to any other portion.  A trap handler that can identify
  and resolve the fault may therefore re-execute the instruction, which then repeats the
  whole transfer from the beginning.

The no-completion guarantees above concern each instruction's own explicit effects.
As for any other instruction, trap entry updates the trap CSRs, and the implicit
accesses performed by address translation may set the accessed and dirty bits of a
page-table entry even when the explicit access subsequently traps.  Both remain
governed by the base privileged architecture and are unaffected by these rules.

Checks occur in the following architectural order.  All forms first validate
the encoded M-register index.  An interoperability or strided form then
checks datatype support, reporting `amestatus.UN` and stopping when the tuple
is unsupported; if supported, it validates the complete register-group span
and then checks the base-address alignment before attempting any memory
access.  `mls.1r` and `mss.1r` skip the datatype and group checks, then check the
base-address alignment before attempting any memory access.  A memory fault can be reported only after these preceding checks have
passed.

[[ame-consistency-model]]
==== Consistency model

AME memory instructions appear to execute in program order on the local hart.

AME memory instructions follow RVWMO at the instruction level.  If the Ztso extension
is implemented, AME memory instructions additionally follow RVTSO at the instruction
level.

Element operations are unordered within the instruction.

AME memory accesses follow the same rules for atomicity as scalar memory accesses that
are misaligned or wider than `XLEN`.

For a strided store whose segment address ranges overlap, the staging order stated in
<<ame-common-memory>> selects the final memory image once the instruction has
completed; it is not an order in which the instruction's memory operations become
visible.  The no-partial-completion rule in <<Memory exceptions>> likewise constrains
what a faulting instruction commits, not what another hart may observe while an
instruction that does not fault is executing.

[NOTE]
--
Ztso only imposes RVTSO at the instruction level; intra-instruction ordering follows
RVWMO regardless of whether Ztso is implemented.

Ordering an AME memory instruction with respect to a non-AME memory instruction needs
nothing AME-specific: the standard `fence` instruction applies, AME loads counting as
memory reads and AME stores as memory writes, and RVWMO already orders accesses to
overlapping addresses without a fence.

A separate consequence of following RVWMO at the instruction level is that element
atomicity is not guaranteed.  An AME transfer may be decomposed into component memory
operations of any granularity, exactly as a misaligned scalar access may be, so a
concurrent observer may see part of an element transferred and the remainder not.
--

=== Operators

AME supports several broad classes of operations:

*  Backend management
*  2D Matrix multiply
*  1D Element-wise/vector
*  Intra-tensor (reduction/expansion/permutation)
*  Register move / data conversion
*  Scalar ingress and data scalar operands
*  Load/store

AME does not support general masking/predication on computational instructions, though a future extension may add support.

==== Backend management

===== `ame.acquire`

`ame.acquire rd, rs1` atomically requests the entire backend. Every applicable
`MS` field must be non-Off; otherwise, the instruction raises an
illegal-instruction exception.

`rs1` contains the acquisition descriptor:

[cols="1,1,3",options="header"]
|===
|Field |Location |Description

|WAIT_MODE
|`1:0`
|Waiting policy

|TIMEOUT_CLASS
|`5:2`
|Bounded-wait class

|RESERVED
|`XLEN-1:6`

|===

`WAIT_MODE=0b00` is TRY and does not wait. `WAIT_MODE=0b01` is BOUNDED_WAIT
and waits for a finite, implementation-defined interval. Other encodings are
reserved. For BOUNDED_WAIT, `TIMEOUT_CLASS` values `0x0` through `0x3` select
SHORT, MEDIUM, LONG, and VERY_LONG; `0xF` is implementation-defined and all
other values are reserved. TRY ignores `TIMEOUT_CLASS`.

An invalid descriptor returns BAD_DESC, and disabled configuration returns
DISABLED. A request from the current owner returns GRANTED without changing
the bound state or `MS`. A new grant atomically binds architectural initial
state, sets `ameown.OWNED` to one, and sets each applicable `MS` field to
Initial. Initial state has zero-valued `M` and `Acc` registers, zero-valued
`Md` and `Ad` descriptors, and reset-valued writable AME CSRs. Failure changes
neither backend binding, `ameown`, nor `MS`.

===== `ame.release`

`ame.release` requires every applicable `MS` field to be non-Off. If the
current context owns the backend, it stops accepting new operations, drains
retired operations and earlier state-save stores, unbinds the state, and
atomically releases ownership.

After release, `ameown.OWNED` is zero and each applicable `MS` field is
Initial. If the current context is not the owner, the instruction is a no-op
that preserves `MS`.



[[ame-common-matmul]]
==== 2-dimensional matrix multiply operations

AME matrix multiplication instructions calculate the matrix product `C = A x B`.
Supported source and accumulator datatype combinations are constrained by
<<ame-common-operand-classes>>.

For *non-packed datatypes* (`pack_factor = 1`), each logical square is `N x N`.
When operand formation produces `N_sq > 1`, the operation pairs logical squares
`A_s` and `B_s` by their zero-based square index.  The accumulator output C is
always `N x N`, and each output element sums `N_sq * N` scalar products.

The untransposed form computes `sum(A[s] x B[s], s = 0 .. N_sq-1)`.  This is
equivalently the product of an `N x (N_sq * N)` A matrix formed by laying the
`A[s]` squares side by side and an `(N_sq * N) x N` B matrix formed by stacking
the `B[s]` squares.  The transpose-A form computes
`sum(transpose(A[s]) x B[s], s = 0 .. N_sq-1)`, and the transpose-B form
computes `sum(A[s] x transpose(B[s]), s = 0 .. N_sq-1)`.  The transposes therefore apply within each logical
square and remain dimensionally valid for every `N_sq`.

The accumulation order for additions inside each dot product is implementation-defined.
That order is fixed within a given implementation, so repeated runs on the same implementation
produce the same result.

Each dot product accumulates numeric products interpreted according to the
source and accumulator datatypes.  The implementation uses its fixed
permutation of the `K` terms and applies the documented overflow, saturation,
floating-point, rounding, and optional fused-product behavior.  Encoded
register bits are never accumulated as untyped bit-vector integers.
Every matrix multiply accumulates: each dot product is seeded with the
pre-instruction accumulator element, and the product is then added to or
subtracted from it.  Software that wants a product alone clears the accumulator
first with `mzero.2d.acc`, which writes the accumulator datatype's semantic
additive zero rather than an all-zero raw bit pattern.
Until a tighter matrix-precision profile is defined, these finite-precision
choices are implementation-defined.  An implementation shall document the
selected behavior, and that behavior shall be deterministic for a given
operation/datatype tuple.

[NOTE]
Different implementations may use different accumulation orders, and therefore may produce
different results (especially for floating-point data).

Formally:

.AME matrix multiplication
[source]
--
def perm(range): implementation-defined permutation over range

# mode is ordinary, transpose-A, or transpose-B
terms = perm((s,q) for s in 0..N_sq-1, q in 0..N-1)

for i in 0..N-1:
  for j in 0..N-1:
    ordinary:   C[i,j] = sum(A_s[i,q] * B_s[q,j] for (s,q) in terms)
    transpose-A:C[i,j] = sum(A_s[q,i] * B_s[q,j] for (s,q) in terms)
    transpose-B:C[i,j] = sum(A_s[i,q] * B_s[j,q] for (s,q) in terms)
--

Matrix multiplication is not commutative (`A*B != B*A` in general),
so operand order must be preserved by software using AME primitives.

AME defines the matrix-multiply instruction variants listed below.
The destination of matrix multiply operations is always an accumulator register.
The operations differ in
whether or not they transpose an input before multiplying,
and whether the product is added to or subtracted from the accumulator.

[cols="1,2,3",options="header"]
|===
| Instruction   | Operation  | Description
| <<ame:doc:inst:mmulacc_2d,mmulacc.2d>>
| `C = C + A × B`
| Matrix multiply accumulate
| <<ame:doc:inst:mmulaccneg_2d,mmulaccneg.2d>>
| `C = C - A × B`
| Negated matrix multiply accumulate
| <<ame:doc:inst:mmulatacc_2d,mmulatacc.2d>>
| `C = C + sum(transpose(A[s]) × B[s], s = 0 .. pack_factor-1)`
| Matrix multiply with transposed A, accumulate
| <<ame:doc:inst:mmulataccneg_2d,mmulataccneg.2d>>
| `C = C - sum(transpose(A[s]) × B[s], s = 0 .. pack_factor-1)`
| Matrix multiply with transposed A, negated accumulate
| <<ame:doc:inst:mmulbtacc_2d,mmulbtacc.2d>>
| `C = C + sum(A[s] × transpose(B[s]), s = 0 .. pack_factor-1)`
| Matrix multiply with transposed B, accumulate
| <<ame:doc:inst:mmulbtaccneg_2d,mmulbtaccneg.2d>>

The floating-point special-value and accuracy behavior of these operations is
defined in <<norm:ame_fp_special_values>>.

For standard integer arithmetic, the mathematical expression is evaluated
without intermediate truncation and converted once to the destination integer
datatype.  A saturating destination clamps an out-of-range result and sets
`amexsat.SAT`; a non-saturating destination retains the low destination-width
bits.  `mhdiff.ew`, `mhdiff.ew.x`, `mmean.ew`, and `mmean.ew.x` round fraction
bits below the destination LSB using the destination datatype's rounding mode
before that conversion.  Custom
datatype tuples may define different conversion rules.

Standard floating-point operations accrue their IEEE exception flags in
`amefflags`; they do not modify `fflags`.  Updates to `amefflags` and `amexsat`
are accumulated locally for the whole instruction and OR-ed into the
architectural CSRs only when destination writes commit.  An instruction that
raises a synchronous exception commits neither destination writes nor status
flag updates.

The `mcmpge.ew` and `mcmplt.ew` families perform ordered comparisons.  For
floating-point sources, a NaN operand makes the comparison false and `-0`
compares equal to `+0`.  A true comparison produces all one bits in the
destination integer element, and a false comparison produces all zero bits.

The `mselge.ew`, `msellt.ew`, `mcmovge.ew`, and `mcmovlt.ew` families do not
perform a numeric or floating-point comparison.  They test the most
significant bit of the raw predicate-element encoding: the `ge` condition is
true when that bit is clear and the `lt` condition is true when that bit is
set.  Consequently, floating-point NaN and zero encodings are treated only by
their sign bit.  An unselected `mselge.ew` or `msellt.ew` element becomes the
destination datatype's semantic zero, including its canonical zero sign.
Shift amounts are reduced modulo the data-source element width.  `mzero.2d.m`
and `mzero.2d.acc` produce the destination datatype's semantic zero; its
encoding need not be all zero bits.
`mrowid.ew` and `mcolid.ew` represent the zero-based coordinate exactly in the
destination datatype.

For `mcmovge.ew` and `mcmovlt.ew`, an unselected destination element is
preserved bit-for-bit.  For `mldexp.ew.x` and `mldexpacc.ew.x`, `X[rs1]` is
zero-extended or low-bit truncated to the width of
<<ame:doc:param:AME_MAX_INT_DTYPE,AME_MAX_INT_DTYPE>> as defined by that
parameter, then interpreted using that integer datatype.  For `mldexpacc.ew`,
`mldexpacc.ew.x`, `mrdexpacc.ew`,
`mmulacc.ew`, `mmulacc.ew.x`, `mmulaccneg.ew`, `mmulaccneg.ew.x`,
`mmuladd.ew`, `mmuladd.ew.x`, `mmulsub.ew`, and `mmulsub.ew.x`, the complete
expression shown by the instruction is evaluated without an intermediate destination
conversion and is converted to the destination datatype once.  In particular,
the multiply-add and multiply-subtract forms have fused semantics.  For a
floating-point tuple, any NaN input, zero multiplied by infinity, or addition
of opposite-signed infinities produces the destination datatype's canonical
quiet NaN; other infinities follow the mathematical expression.  A finite
result is rounded once using the destination datatype's rounding mode and
accrues `amefflags` as described above.

A signaling NaN is treated as a NaN and the result is quieted.  If a required
mathematical infinity is not representable by the destination datatype, the
result saturates to the signed minimum or maximum, as appropriate.  A tuple
that cannot represent a required NaN result is unsupported.

Floating-point exceptional conditions are ordinary data results after the
datatype tuple has been accepted: they do not raise an exception or set
`amestatus.UN`.  For standard floating-point datatypes, `amefflags` uses the
same five accrued exception classes as RISC-V `fflags`, with tininess detected
after rounding:

* `NV` is set for a signaling NaN or an invalid operation, including an
  infinity-minus-itself form, zero multiplied by infinity, a finite negative
  square root, or an invalid floating-point-to-integer conversion.  Propagating
  a quiet NaN alone does not set `NV`.
* `DZ` is set when an exact infinite result arises from finite inputs because
  of a pole at zero, including reciprocal or reciprocal-square-root of zero
  and `log2(±0)`.
* `OF` is set when the rounded result's magnitude exceeds the destination's
  finite range.  Such a result also sets `NX`.
* `UF` is set when the result is tiny after rounding and inexact.  Such a
  result also sets `NX`.
* `NX` is set whenever the delivered finite result differs from the exact
  mathematical result because of rounding, including an implementation-defined
  approximation that is not exact.

Exact operations and exact conversions set none of these flags.  A custom
floating-point datatype definition must specify equivalent flag conditions
for every supported tuple that can update `amefflags`; otherwise that tuple is
unsupported.

introduce an additional zero term, and every binary addition is rounded to the
destination datatype as specified in <<norm:ame_fp_special_values>>.  Minimum
and maximum NaN and signed-zero behavior is also defined there.

pre-instruction value.  A later contribution to the same coordinate reads the
staged result produced by the preceding contribution, then stages its own
result.  Thus a scatter formula's RHS `D` denotes the evolving staged value
for a collision, while all other source operands retain the common
pre-instruction snapshot behavior.

==== Register move / data conversion

`<<ame:doc:inst:mmov_m_m,mmov.m.m>>` copies all elements from one `M` register to another.
Datatype combinations for these operations are constrained by
<<ame-common-operand-classes>>.
`<<ame:doc:inst:mmov_m_a,mmov.m.a>>` copies all elements from an `Acc` register to an `M` register.
`<<ame:doc:inst:mmov_a_m,mmov.a.m>>` copies all elements from an `M` register to an `Acc` register.
In all three cases, the source and destination datatypes must match; if they differ, `amestatus.UN` is set and the destination is left unchanged.

`<<ame:doc:inst:mzero_2d_acc,mzero.2d.acc>>` writes zero to every element of an `Acc` register,
typically used to initialize an accumulator before a matrix multiply sequence.
`<<ame:doc:inst:mzero_2d_m,mzero.2d.m>>` writes zero in the configured datatype to every logical
element of an `M` register group, including packed element positions.
`<<ame:doc:inst:mrowid_ew,mrowid.ew>>` and `<<ame:doc:inst:mcolid_ew,mcolid.ew>>` form the index
group of the 1-dimensional elementwise instructions: they write the zero-based row or column
index, represented in the configured datatype, to every logical element of an `M` register group.

`<<ame:doc:inst:mconv_ew,mconv.ew>>` converts element data from one datatype to another.
The source and destination datatypes may each be packed or non-packed, and both operands
are formed by the common operand-formation rules with `N_sq = max(pack_factor)`.
A packed-to-non-packed conversion expands one packed `M` register into `pack_factor` consecutive
non-packed `M` registers; a non-packed-to-packed conversion does the reverse.
The indexed <<ame:doc:inst:mpack_ew_x,mpack.ew.x>> and
<<ame:doc:inst:munpack_ew_x,munpack.ew.x>> forms convert one selected square at a time,
reducing register pressure when a full expand or compress is not required.

==== Scalars

AME provides an explicit typed scalar ingress instruction and data-scalar
elementwise forms.  Software can therefore use a converted scalar repeatedly
through an M register, or use a data scalar directly without allocating an M
register for it.

===== Scalar ingress and data scalar operands

`mbcast.m.x` is the explicit scalar ingress instruction. It interprets an X-register
bit pattern using a datatype encoding supplied in another X register, converts the
value to the destination `Md` datatype using the common conversion rules, and broadcasts the converted
value to every logical element of the destination M operand.

Data scalar `.ew.x` instructions use `CSR[amestype]` for the source scalar
type. The scalar is converted to the tensor operand datatype before the ordinary
same-datatype operation is evaluated. This keeps the operation support table
polymorphic without requiring a separate mixed-type tuple for every instruction.

Shift amounts, indices, offsets, and other control scalar operands are fixed-type
integer values defined by their instruction. They do not read
`CSR[amestype]` and do not undergo AME datatype conversion.

[cols="1,2,3",options="header"]
|===
| Instruction | Operation | Description
| <<ame:doc:inst:mbcast_m_x,mbcast.m.x>>
| `D[i] = convert(X[rs1], source datatype X[rs2], destination datatype Md[md])`
| Convert one X scalar and broadcast it to an M operand
|===

===== Debug scalar element moves

The `mmove` family provides single-element moves between an X register and a
fixed position inside one M register, intended for debugging.  Each
instruction defines its own element size (8, 16, 32, or 64 bits) and accesses
the register through the row-major layout transformation, viewed as `N` rows
of `row_elements` elements of that size; it uses neither
`CSR[amestype]` nor the register datatype in `Md`.

==== Load and store

AME load and store instructions transfer squares between `M` registers and memory.
Square variants (`mls.rm`, `mls.cm`, `mss.rm`, `mss.cm`) access contiguous memory,
while strided variants (`mls.st`, `mls.tst`, `mss.st`, `mss.tst`) access
non-contiguous memory through a programmable byte stride supplied in an integer register.
The whole-register instructions (`mls.1r`, `mss.1r`) transfer one physical M register in
row-major order at a fixed element size of `AME_UNIT_DATATYPE_SIZE`, without reading a
datatype register.  The interoperability and strided instructions determine the
element datatype from the programmed datatype of the destination or source register.
The memory layouts, the base-address alignment requirement, and the exception behavior of
these instructions are defined in <<ame-common-memory>>.
