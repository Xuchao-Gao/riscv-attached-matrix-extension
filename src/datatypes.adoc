[[datatypes]]
=== Datatypes

AME supports up to `2^32 - 1` unique datatypes, half of which are reserved for
custom use.  The value zero is reserved to mean uninitialized.  Here,
"uninitialized" describes the datatype descriptor, not whether the
corresponding `M` or `Acc` register data has previously been written.
Instruction handling of zero, unknown, and unsupported descriptors is defined
by <<ame-common-datatype-support,the common datatype-tuple rules>>.

[NOTE]
--
The datatype registers are similar to WARL CSR fields, so implementations only
need to support enough state to represent the datatypes they support.  For
example, an implementation that supports only two datatypes needs only enough
physical state to represent those datatypes plus uninitialized.
--

Implementations may choose which standard and custom datatypes they support.
A legal implementation may support no standard datatypes or no custom
datatypes.

[NOTE]
--
Profiles will likely mandate a minimum supported set.
--

`M` register datatype descriptors are written with
<<ame:doc:inst:msettyp,msettyp>> and read with
<<ame:doc:inst:mgettyp,mgettyp>>.  `Acc` register datatype descriptors are
written with <<ame:doc:inst:asettyp,asettyp>> and read with
<<ame:doc:inst:agettyp,agettyp>>.  Their validation and architectural effects
are defined by the detailed instruction descriptions and
<<ame-common-datatype-support,the common datatype contract>>.

[[datatype-descriptor-encoding]]
==== Datatype descriptor encoding

AME uses a 32-bit datatype specifier encoded as follows:

|===
| Position | Meaning

| `31`   | `0` = standard, `1` = custom
| `30:8` | Datatype properties
| `7:0`  | Datatype size, in bits
|===

Standard datatype encodings will never begin with '1'.
Conforming implementations must encode custom datatypes with a leading '1'.

By convention, the lowest bits after the datatype size are used to specify the datatype family
(e.g., integer, floating-point) and the upper bits are used first to distinguish types within the
family. This allows the number of families to grow over time if needed without needing to know
a-priori how many families will need to be supported over time.

AME follows an encoding convention, and the datatypes defined in AME v1.0 follow that convention.
However, each datatype encoding should still be treated as an enumeration value, not as a format
that software should decode by assumption.
RISC-V may introduce future data types that do not follow the current convention.


==== Integer datatype class

Integer type properties occupy bits `30:9` when bit 8 is `0`.
Integer types are distinguished by size/precision, signedness, saturation behavior,
and rounding mode.

|===
| Position | Field | Values

| `31`
| Custom
| `0`

| `30`
| Sign
| `0` = unsigned, `1` = signed

| `29`
| Saturation
| `1` = saturate, `0` - overflow

| `28:27`
| Rounding mode
| `00` = RNU, `01` = RNE, `10` = RDN, `11` = ROD

| `26:9`
| (reserved)
| Must be zero

| `8`
| Integer specifier
| `0`

| `7:0`
| Size
| Size, in bits of the datatype

|===

Integer types are two's complement binary numbers.

The `Rnd` column is shown as `xx` (don't care): each standard integer type
name denotes the four encodings obtained with the four rounding-mode values.
These encodings share size, signedness, and saturation behavior, and differ
only in the rounding of sub-LSB intermediate results.
The operation-level meaning of these modes is defined by
<<ame-common-integer,the standard integer operation semantics>>.

==== IEEE floating-point class

The IEEE floating-point class holds data types that either are IEEE 754 floating point or
behave similarly to it with small modifications.

We classify datatype in the class by whether or not it is signed, exponent size, presence of NaN,
presence of infinity, and rounding mode. The mantissa width is implicit:
`mantissa_bits = element_size - exp_width - 1` (one bit for the sign).

.IEEE floating-point class encoding convention
|===
| Position | Field | Values

| `31`
| Custom
| `0`

| `30:26`
| exp_width
| Number of exponent bits (e.g., `5` for FP16, `8` for BF16/FP32)

| `25:22`
| rounding_mode
| `0000` = RNE, `0001` = RTZ, `0010` = RDN, `0011` = RUP, `0100` = RMM, `0101` = RNO, others reserved

| `21`
| Inf
| `1` = ±infinity if signed, infinity if unsigned, `0` = Saturate to min/max

| `20`
| Denorm
| `1` = Use denormals, `0` = flush-to-zero

| `19:9`
| (reserved)
| Must be zero

| `8`
| FP
| `1`

| `7:0`
| Size
| Size, in bits of the datatype

|===

|            h| Std  h| Exp_W    h| Rnd      h| Inf  h| Denorm  h|  Rsv    h|  FP  h|  Size

[[datatype-discovery]]
==== Datatype and operation discovery

The AME datatype namespace and the set of possible operation/datatype tuples
are intentionally larger than an implementation is expected to support.
Software discovers whether an `M` or `Acc` datatype is accepted by executing
`msettyp` or `asettyp` and inspecting
<<ame:doc:csr_field:amestatus:UN,amestatus.UN>>.  It discovers whether an exact
operation/datatype tuple is supported by executing that operation and checking
the same field.  Unsupported tuples follow
<<norm:ame_op_supported_contract,the common unsupported-datatype-tuple contract>>.

Example probe sequences are provided in
<<datatype-discovery-examples,the datatype and operation discovery examples>>.
